## Floating-Point Environment Instructions

### `.get_fpenv` - Read Floating-Point Control/Status

```
let i32:%out = .get_fpenv()
```

Reads the processor's floating-point control and status register and returns it as an opaque 32-bit bit-pattern. On x86 with SSE, this corresponds to `STMXCSR` (reading `MXCSR`). The returned value encodes, among other fields: the current rounding mode, the flush-to-zero (FTZ) and denormals-are-zero (DAZ) flags, the floating-point exception mask bits, and the sticky floating-point exception status flags.

The bit layout of the returned value is **implementation-defined and matches the native `MXCSR` encoding** on x86 targets; portable code must not construct or inspect values for this register by hand and should instead obtain values exclusively via `.get_fpenv` and treat them as opaque tokens to be round-tripped through `.set_fpenv`. For inspecting or modifying specific fields (rounding mode, FTZ/DAZ, exception masks) in a portable way, use `.fpenv_get_field` / `.fpenv_set_field` below.

No input. No attributes.

### `.set_fpenv` - Write Floating-Point Control/Status

```
.set_fpenv(i32:%env)
```

Writes `%env` to the processor's floating-point control and status register, replacing its entire contents. Corresponds to `LDMXCSR` on x86 with SSE. `%env` should normally be a value previously obtained from `.get_fpenv` (possibly modified via `.fpenv_get_field` / `.fpenv_set_field`), to ensure reserved bits are preserved correctly - writing an arbitrary bit pattern with reserved bits set to incorrect values is undefined behavior.

No output.

- `#[volatile]` - prevents the optimizer from eliminating, reordering across other floating-point operations, or merging redundant `.set_fpenv` calls. Without this attribute, the optimizer may hoist, sink, deduplicate, or eliminate `.set_fpenv` calls that it can prove have no observable effect on floating-point results (e.g. two consecutive identical `.set_fpenv` calls with no intervening floating-point op may be merged). Code that sets the environment specifically to influence the *side effects* of nearby floating-point ops (rather than their results) - such as deliberately triggering or suppressing FP exception traps - should always use `#[volatile]`.

### `.fpenv_get_field` - Extract a Field from an FP Environment Value

```
let i32:%out = .fpenv_get_field(i32:%env, str:field)
```

Extracts a named field from an opaque FP environment value (as returned by `.get_fpenv`) in a portable, implementation-independent way, returning the field's value right-justified in the result (i.e. as a small integer, not a bit-masked-in-place value).

`field` must be a compile-time string literal, one of:

- `"round"` - current rounding mode. Returns one of `0` (round to nearest, ties to even), `1` (round toward negative infinity), `2` (round toward positive infinity), `3` (round toward zero).
- `"ftz"` - flush-to-zero flag. Returns `0` or `1`.
- `"daz"` - denormals-are-zero flag. Returns `0` or `1`.
- `"except_mask"` - the five IEEE exception mask bits (invalid, denormal, divide-by-zero, overflow, underflow, inexact), packed as a 6-bit value in a fixed implementation-independent bit order (bit 0 = invalid, bit 1 = denormal, bit 2 = divide-by-zero, bit 3 = overflow, bit 4 = underflow, bit 5 = inexact; `1` = masked/suppressed, `0` = unmasked/enabled).
- `"except_status"` - the same six exceptions, but the *sticky status* flags (which exceptions have occurred since last cleared), same bit order.

No attributes.

### `.fpenv_set_field` - Set a Field in an FP Environment Value

```
let i32:%out = .fpenv_set_field(i32:%env, str:field, i32:%value)
```

Returns a copy of `%env` with the named field replaced by `%value`, leaving all other bits (including reserved bits) unchanged. `field` accepts the same set of names as `.fpenv_get_field`, with the same value encodings expected for `%value`. Does not itself modify the processor state - the result must be passed to `.set_fpenv` to take effect. This split (read environment → modify field → write environment) is the recommended pattern for e.g. temporarily switching rounding mode:

```
let i32:%saved = .get_fpenv()
let i32:%modified = .fpenv_set_field(%saved, "round", 1i32)
.set_fpenv(%modified) #[volatile]
... ; perform operations under round-toward-negative-infinity
.set_fpenv(%saved) #[volatile]
```

For `"except_status"`, setting bits is interpreted as *clearing* the corresponding sticky exception flags (writing `1` to a status bit clears it, matching x86 `MXCSR` semantics for exception flags) - `%value` bit `i` set to `1` clears exception `i`'s status, `0` leaves it unchanged. This is the only field where `.fpenv_set_field` does not perform a simple overwrite of the corresponding bits; all other fields overwrite directly.

No attributes.

## Notes on Determinism and Optimization

`.rdtsc`, `.rdtscp`, `.rdrand`, `.rdseed`, and `.get_fpenv` are all treated by the optimizer as **opaque, non-deterministic, side-effecting** calls: the optimizer must not constant-fold, common-subexpression-eliminate, hoist out of loops, or reorder these relative to each other, even though none of them carry `#[volatile]` by default (their non-determinism alone is sufficient to prevent these transforms - `#[volatile]` is reserved for cases like `.set_fpenv` where the concern is observable *side effects on other code* rather than the instruction's own result varying).

`.set_fpenv`, `.fpenv_get_field`, and `.fpenv_set_field` do not read entropy or timing hardware and are otherwise pure with respect to the values they manipulate (`.fpenv_get_field` / `.fpenv_set_field` are ordinary pure functions over `i32`), but `.set_fpenv` writes processor state that affects the *behavior* of all subsequent floating-point instructions, which is why it requires `#[volatile]` to suppress reordering when that behavioral effect (rather than just numeric results) matters.

## Modifications to Existing Instructions (continued)

### `.cpuid` - New Instruction Required by `.rdtsc` Serialization Idiom

```
let {i32, i32, i32, i32}:%out = .cpuid(i32:%leaf, i32:%subleaf)
```

Executes the x86 `CPUID` instruction with `EAX = leaf` and `ECX = subleaf`, returning a struct `{eax: i32, ebx: i32, ecx: i32, edx: i32}` containing the resulting register values. `CPUID` is fully serializing (acts as a barrier against out-of-order execution of surrounding instructions), which is why it is the traditional pairing with `.rdtsc` for serialized timestamp reads (the "cpuid; rdtsc; ...; rdtsc; cpuid" benchmarking idiom).

Both `%leaf` and `%subleaf` may be runtime values (unlike most other hardware-feature-querying mechanisms, `CPUID` does not require compile-time-constant inputs). However, the *set of valid leaves* and the *meaning* of the returned register fields are entirely processor- and leaf-dependent and outside the scope of this instruction's semantics - callers are responsible for knowing which leaves are valid and how to interpret the results.

No attributes.


## Crypto-Extension Instructions

These are thin, opaque wrappers around AES-NI, PCLMULQDQ, SHA extensions, and SSE4.2 CRC32 - same category as `.rdrand`/`.cpuid`/cache control: no portable expression exists, the backend emits the named instruction directly, and the optimizer treats them as black boxes with respect to their bit-pattern semantics (pure w.r.t. inputs, but opaque - don't constant-fold byte-for-byte unless inputs are fully known compile-time constants, which is allowed but rarely useful).

---

### AES Instructions

All operate on a 128-bit AES state/key represented as `<i8,16>` (a 16-byte block - the natural representation for a cipher block). No vector-of-blocks form; loop over blocks explicitly.

#### `.aesenc` - AES Encrypt Round

```
let <i8,16>:%out = .aesenc(<i8,16>:%state, <i8,16>:%roundkey)
```

Performs one AES encryption round (ShiftRows, SubBytes, MixColumns, AddRoundKey) on `state` using `roundkey`. Corresponds to `AESENC`. No attributes.

#### `.aesenclast` - AES Encrypt Last Round

```
let <i8,16>:%out = .aesenclast(<i8,16>:%state, <i8,16>:%roundkey)
```

Same as `.aesenc` but omits MixColumns (final round). Corresponds to `AESENCLAST`. No attributes.

#### `.aesdec` - AES Decrypt Round

```
let <i8,16>:%out = .aesdec(<i8,16>:%state, <i8,16>:%roundkey)
```

Performs one AES decryption round (InvShiftRows, InvSubBytes, InvMixColumns, AddRoundKey). Corresponds to `AESDEC`. No attributes.

#### `.aesdeclast` - AES Decrypt Last Round

```
let <i8,16>:%out = .aesdeclast(<i8,16>:%state, <i8,16>:%roundkey)
```

Same as `.aesdec` but omits InvMixColumns (final round). Corresponds to `AESDECLAST`. No attributes.

#### `.aesimc` - AES Inverse Mix Columns

```
let <i8,16>:%out = .aesimc(<i8,16>:%roundkey)
```

Applies InvMixColumns to a round key, converting an encryption round key into the form required for `.aesdec`. Used when expanding a decryption key schedule. Corresponds to `AESIMC`. No attributes.

#### `.aeskeygenassist` - AES Key Generation Assist

```
let <i8,16>:%out = .aeskeygenassist(<i8,16>:%a, i8:rcon)
```

Assists in AES round-key generation: performs `SubWord` on the high and low 32-bit words of `a`, rotates, and XORs in the round constant `rcon`. `rcon` must be a compile-time integer literal (only the low byte is meaningful; high bits should be `0`). Corresponds to `AESKEYGENASSIST`. The caller is responsible for the shuffles/XORs that turn this into a full expanded key (the instruction itself does not loop over rounds). No attributes.

---

### Carry-less Multiply

#### `.clmul` - Carry-less (GF(2)) Multiply

```
let T2:%out = .clmul(T1:%a, T1:%b)
```

Multiplies `a` and `b` as polynomials over GF(2): each bit of the product is the XOR (not sum) of the corresponding partial-product bits - i.e. multiplication with no carry propagation. Returns the full double-width product in `T2`. `T1` must be `i64`; `T2` must be `i128`. Corresponds to `PCLMULQDQ` (the immediate operand that selects which 64-bit half of each 128-bit register to feed in is a pure register-allocation detail and is handled by the backend - this instruction exposes only the semantic 64×64→128 carry-less product). Primary use cases: GHASH (AES-GCM), CRC computation, Reed–Solomon / erasure coding. No attributes.

---

### SHA Extensions

All operate on the 128-bit "state quad" representation `<i32,4>` used by Intel's SHA extension documentation (four 32-bit words packed into one 128-bit register). No vector-of-states form.

#### `.sha1rnds4` - SHA1 Four Rounds

```
let <i32,4>:%out = .sha1rnds4(<i32,4>:%abcd, <i32,4>:%msg, i8:func)
```

Performs four rounds of SHA-1 on `abcd` using message-schedule input `msg`, selecting the round function via `func`. `func` must be a compile-time literal in `[0, 3]` (selects `f1`/`f2`/`f3`/`f4` per the SHA-1 spec - `0` = rounds 0–19, `1` = rounds 20–39, `2` = rounds 40–59, `3` = rounds 60–79). Corresponds to `SHA1RNDS4`. No other attributes.

#### `.sha1nexte` - SHA1 Next E

```
let <i32,4>:%out = .sha1nexte(<i32,4>:%abcd, <i32,4>:%e)
```

Computes the rotated-add needed to advance the SHA-1 `e` working variable into the next four-round group. Corresponds to `SHA1NEXTE`. No attributes.

#### `.sha1msg1` - SHA1 Message Schedule Step 1

```
let <i32,4>:%out = .sha1msg1(<i32,4>:%a, <i32,4>:%b)
```

Performs the first intermediate step of SHA-1 message-schedule expansion (`W[i] = W[i-3] XOR W[i-16]`-style combination over the packed words). Corresponds to `SHA1MSG1`. No attributes.

#### `.sha1msg2` - SHA1 Message Schedule Step 2

```
let <i32,4>:%out = .sha1msg2(<i32,4>:%a, <i32,4>:%b)
```

Performs the second step of SHA-1 message-schedule expansion, completing the rotate-XOR chain begun by `.sha1msg1`. Corresponds to `SHA1MSG2`. No attributes.

#### `.sha256rnds2` - SHA256 Two Rounds

```
let <i32,4>:%out = .sha256rnds2(<i32,4>:%abef, <i32,4>:%cdgh, <i32,4>:%wk)
```

Performs two rounds of SHA-256 compression on the state halves `abef`/`cdgh`, using `wk` (two packed message-schedule words plus round constants, pre-summed by the caller). Corresponds to `SHA256RNDS2`, with the implicit `XMM0` operand made explicit as `%wk`. No attributes.

#### `.sha256msg1` - SHA256 Message Schedule Step 1

```
let <i32,4>:%out = .sha256msg1(<i32,4>:%a, <i32,4>:%b)
```

First step of SHA-256 message-schedule expansion (`σ0` contribution). Corresponds to `SHA256MSG1`. No attributes.

#### `.sha256msg2` - SHA256 Message Schedule Step 2

```
let <i32,4>:%out = .sha256msg2(<i32,4>:%a, <i32,4>:%b)
```

Second step of SHA-256 message-schedule expansion (`σ1` contribution), completing the value begun by `.sha256msg1`. Corresponds to `SHA256MSG2`. No attributes.

---

### CRC32 Instruction

#### `.crc32` - CRC32C Checksum Update

```
let T2:%out = .crc32(T2:%acc, T1:%data)
```

Updates a running CRC32C (Castagnoli polynomial, `0x1EDC6F41`) checksum: feeds `data` through the CRC, combining with the accumulator `acc`, and returns the updated checksum. Corresponds to the SSE4.2 `CRC32` instruction.

- `T2` (accumulator/output) must be `i32` or `i64`.
- `T1` (data chunk) must be `i8`, `i16`, or `i32` when `T2` is `i32`; or `i8` or `i64` when `T2` is `i64` (mirroring the operand-size restrictions of the hardware `CRC32 r32, r/m{8,16,32}` and `CRC32 r64, r/m{8,64}` forms). Any other `(T2, T1)` pairing is a compile error.

No attributes. To checksum a buffer, the caller loops, loading successive chunks and threading `%out` of one call into `%acc` of the next; the initial accumulator is conventionally `0xFFFFFFFF` (or its `i64` equivalent), per the standard CRC32C convention - the instruction itself does not impose an initial value.

---

### Notes

- All instructions above are pure functions of their operands (deterministic, no hidden state, no memory access) and may be constant-folded if all operands are compile-time constants, common-subexpression-eliminated, and reordered freely - unlike `.rdrand`/`.rdtsc`, there is no non-determinism here, only opacity of *meaning* to the optimizer.
- None of these instructions fault or have alignment requirements; they operate purely on register values, so no `#[align]`/`#[volatile]`/`#[atomic]` family applies to any of them.
- `GF2P8AFFINEQB`/`GF2P8AFFINEINVQB`/`GF2P8MULB` (GFNI) and `VAES`/`VPCLMULQDQ` (AVX-512 widened forms operating on `<i8,32>`/`<i8,64>`) are deliberately left out of this pass - they'd be natural follow-ups (wider vector forms of `.aesenc`/`.clmul` etc.) but aren't required for baseline AES-GCM/SHA support.


Here's a proposed addition for each.

## `.syscall`

```
let i64:%out = .syscall(i64:%nr, i64:%arg1, i64:%arg2, i64:%arg3, i64:%arg4, i64:%arg5, i64:%arg6)
```

Issues the x86_64 Linux `SYSCALL` instruction. `%nr` goes in `rax`; `%arg1`–`%arg6` map to `rdi, rsi, rdx, r10, r8, r9` in order. The argument list is variadic with `0–6` arguments (use the form with however many the target syscall needs - extra unused trailing args are simply omitted, not zero-filled). All operands and the result must be `i64`; pointers must go through `.ptr_to_int` first and results that are pointers come back through `.int_to_ptr`.

Semantics: treated as an arbitrary external call with unknown side effects - may read/write any memory the process can address, may block, may not return, may invalidate previously-established `.invariant_start` regions if the kernel writes through aliased mappings, etc. The optimizer must not reorder `.syscall` relative to memory operations, must not CSE two `.syscall`s even with identical arguments, and must not eliminate one even if `%out` is unused, unless `#[nosideeffect]` is explicitly given. The backend is responsible for saving/restoring `rcx` and `r11` (clobbered by `SYSCALL` itself for return address and flags) and any other registers the calling convention requires live across the instruction.

Attributes:
- `#[noreturn]` - for syscalls that never return on success (`exit`, `exit_group`, a successful `execve`); `.syscall` with no output variable is then permitted.
- `#[nosideeffect]` - opt-in assertion that this specific call (e.g. `getpid`, `gettid`) has no effect beyond producing its return value, allowing DCE/CSE. Off by default; misuse is UB the same as misusing `#[pure]` on `.call`.

No attribute is provided for "check return value for negative errno" - that's a userspace convention the frontend encodes with ordinary `.lt`/`.select`, not an ISA concern.

## CET Shadow Stack

These mirror `.endbr64` in spirit: on hardware/OS configurations where `CR4.CET_SS` is disabled, every one of these executes as a documented no-op (per the Intel SDM), so they're safe to emit unconditionally - they don't need feature-detection to avoid UB, only to avoid being *useless*. None of these fault on CET-disabled hardware; they're all opaque side-effecting instructions w.r.t. an implicit "shadow stack" piece of architectural state that the optimizer must not reorder relative to `.call`/`.ret`/each other.

#### `.rdssp` - Read Shadow Stack Pointer

```
let ptr:%out = .rdssp()
```

Returns the current value of `SSP` (shadow stack pointer) as a `ptr`. Corresponds to `RDSSPQ`. On CET-SS-disabled hardware, returns `0` (per spec, `RDSSPQ` is a no-op and the destination register is left unmodified - so in practice the frontend should treat the result as meaningful *only* when CET-SS is known to be active; document this as implementation-defined-on-disabled-hardware rather than UB). No attributes.

#### `.incssp` - Increment Shadow Stack Pointer

```
.incssp(i64:%count)
```

Pops `%count` 8-byte slots off the shadow stack (advances `SSP` by `8 * count`), reading and discarding/validating each popped value. Corresponds to `INCSSPQ`. `%count` must be `>= 1`; behavior for `0` matches the hardware (treated as `1` per the SDM's note - document this quirk rather than special-case it). Used when unwinding multiple frames at once (e.g. `longjmp`, exception-style multi-level returns in a language that *does* have its own non-LLVM-exception unwinding). No output. No attributes.

#### `.saveprevssp` / `.rstorssp` - Shadow Stack Switch

```
.saveprevssp()
.rstorssp(ptr:%token_addr)
```

`.saveprevssp` pushes a "previous-SSP token" onto the *current* shadow stack, encoding the SSP value that was active before a switch - corresponds to `SAVEPREVSSP`, normally executed immediately after switching `SSP` (e.g. via `.rstorssp` to a new stack) so the old stack's continuation point is recorded. `.rstorssp` loads `SSP` from the restore-token at `%token_addr` and validates it (the token must have been created by a prior `.saveprevssp`/equivalent on that shadow stack, with the "busy" bit set appropriately) - corresponds to `RSTORSSP`. These two are the building blocks for shadow-stack-aware coroutines/green-threads/signal handlers, where each stack needs its own shadow stack and switching between them requires updating `SSP` in lockstep with the data-stack pointer. Both `#[volatile]` implicitly (never reorderable, never eliminable). No additional attributes.

#### `.setssbsy` - Set Shadow Stack Busy

```
.setssbsy()
```

Sets the "busy" bit on the current shadow-stack's supervisor token, completing the activation sequence after `.rstorssp` for a *new* shadow stack (one that hasn't been used before, vs. one being resumed). Corresponds to `SETSSBSY`. No output. No attributes.

#### `.wrss` - Write to Shadow Stack

```
.wrss(T:%value, ptr:%addr)
```

Writes `%value` directly into shadow-stack memory at `%addr`, bypassing the normal write-protection that the shadow stack otherwise has against ordinary `.store`. Corresponds to `WRSSQ`/`WRSSD` depending on width. `T` must be `i32` or `i64`. Requires the CPU's "user-mode WRSS" bit to be enabled by the OS (`CR4.CET_SS` + `MSR_IA32_U_CET.WRSS_EN`); on hardware/configs where it isn't, this faults (`#GP`) rather than no-opping - unlike the others in this group, `.wrss` is *not* safe to emit unconditionally and should only be used in code paths gated on a runtime feature check (via `.cpuid`/CET-enablement query). `#[volatile]` implicitly. No additional attributes.

A normal `.store` to a shadow-stack address is itself a `#GP` fault when CET-SS is active for that thread - this is existing-instruction behavior worth documenting in `.store`'s notes rather than adding new attributes there, since it's a property of the *address*, not the store.

## BMI1 Conveniences

All three: `T` must be `i32` or `i64` (matches the BMI1 register-form encodings; `LEA`/AND-based equivalents handle other widths, so these aren't extended to general `iN`). No attributes - behavior is well-defined for all inputs including `0` (all three are no-ops/produce `0` when the input is `0`, matching `AND/NEG/XOR` composition).

#### `.blsi` - Isolate Lowest Set Bit

```
let T:%out = .blsi(T:%input)
```

Returns a value with only the lowest set bit of `%input` set (all others cleared); `0` if `%input` is `0`. Equivalent to `x & -x`. Corresponds to `BLSI`.

#### `.blsr` - Reset Lowest Set Bit

```
let T:%out = .blsr(T:%input)
```

Returns `%input` with its lowest set bit cleared; `0` if `%input` is `0`. Equivalent to `x & (x-1)`. Corresponds to `BLSR`. The classic "clear lowest set bit" idiom used in popcount loops and bitset iteration.

#### `.blsmsk` - Get Mask Up To Lowest Set Bit

```
let T:%out = .blsmsk(T:%input)
```

Returns a mask with all bits set up to and including the lowest set bit of `%input` (e.g. `0b10100 -> 0b00111`); all bits set (`-1`) if `%input` is `0`. Equivalent to `x ^ (x-1)`. Corresponds to `BLSMSK`.

I'd leave `BEXTR`/`BZHI`/`PDEP`-adjacent "extract a bitfield given a packed (start,len)" instruction out for now - `BEXTR`'s packed-control-register convention is awkward to expose cleanly and is trivially `(x >> start) & mask(len)` via existing `.lshr`/`.and`, so unlike `.blsi`/`.blsr`/`.blsmsk` (which are single-bit idioms worth recognizing atomically), this one doesn't pull its weight as a primitive.

## f80 and FP Environment

Short answer: **`.get_fpenv`/`.set_fpenv`/`.fpenv_get_field`/`.fpenv_set_field` should remain explicitly MXCSR-only and explicitly *not* apply to `f80`**, and you want a parallel x87 set rather than overloading the existing ones - the two control registers have genuinely different field layouts (x87 has a "precision control" field with no MXCSR equivalent; MXCSR has FTZ/DAZ with no x87 equivalent), and critically, **the status (sticky exception) bits live in a different register (`FSW`) than the control bits (`FCW`) on x87**, whereas on SSE both live together in `MXCSR`. That asymmetry breaks the clean `.get_fpenv`/round-trip-through-`.set_fpenv` pattern you have now, so it's better as its own small instruction group rather than a bolted-on attribute.

#### `.get_fpenv87` / `.set_fpenv87` - x87 Control Word

```
let i16:%out = .get_fpenv87()
.set_fpenv87(i16:%env)
```

Reads/writes the x87 FPU control word (`FCW`), via `FNSTCW`/`FLDCW`. Opaque `i16` token, round-tripped the same way `.get_fpenv`/`.set_fpenv` round-trip `MXCSR`. `.set_fpenv87` requires `#[volatile]` for the same reason `.set_fpenv` does (suppressing reordering when the *side effect* on subsequent f80 ops, not the FCW value itself, is what matters).

#### `.fpenv87_get_field` / `.fpenv87_set_field`

```
let i32:%out = .fpenv87_get_field(i16:%env, str:field)
let i16:%out = .fpenv87_set_field(i16:%env, str:field, i32:%value)
```

Same shape as the MXCSR versions. `field` is one of:
- `"round"` - same 4-value encoding as the MXCSR `"round"` field (0=nearest-even, 1=toward `-inf`, 2=toward `+inf`, 3=toward zero). x87 encodes this in `FCW` bits 10–11, same numeric meaning, different bit position - the field accessor hides that.
- `"precision"` - **x87-only field, no MXCSR equivalent.** Controls the internal computation precision for x87 arithmetic independent of the operand type: `0` = single (24-bit mantissa), `2` = double (53-bit), `3` = extended/80-bit (64-bit mantissa). `1` is reserved/undefined - `.fpenv87_set_field` with `1` is a compile error if the value is a compile-time constant, UB otherwise. Note this is largely a historical footgun (x87's "set precision to double so `f80` intermediates round like `f64`" trick) and most code should leave it at `3`.
- `"except_mask"` - same 6-bit packed layout/order as the MXCSR version (invalid, denormal, divide-by-zero, overflow, underflow, inexact; `1`=masked).
- No `"ftz"`/`"daz"` - x87 has no equivalent; requesting these is a compile error.

#### `.get_fpstatus87` / `.clear_fpstatus87` - x87 Status Word

```
let i16:%out = .get_fpstatus87()
.clear_fpstatus87()
```

`.get_fpstatus87` reads `FSW` via `FNSTSW` (read-only - there is no `FLDSW`). Use `.fpenv87_get_field` semantics conceptually on this value with `field = "except_status"` (same 6-bit order as MXCSR's `"except_status"`) to extract individual sticky flags - but note `.fpenv87_set_field` does **not** accept `"except_status"` as a settable field on an `i16` you'd feed back into `.set_fpenv87`, because writing `FCW` via `FLDCW` does not affect `FSW` at all.

`.clear_fpstatus87` clears **all** sticky exception flags in `FSW` at once via `FNCLEX` - unlike the MXCSR path (`.fpenv_set_field(..., "except_status", ...)` can clear individual bits by writing back through `.set_fpenv`), x87 only supports clear-all. `#[volatile]`, no inputs/outputs beyond that.

#### Net effect on the existing instructions

Document explicitly in `.get_fpenv`/`.set_fpenv`/`.fpenv_get_field`/`.fpenv_set_field`: *"These instructions read/write `MXCSR` only and have no effect on `f80` arithmetic; rounding mode, precision, and exception state for `f80` operations are controlled exclusively via `.get_fpenv87`/`.set_fpenv87`/`.get_fpstatus87`/`.clear_fpstatus87`."* That one sentence closes the gap without touching the existing four instructions' signatures at all.
